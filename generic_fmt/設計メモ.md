# 汎用FMT（縦持ち）設計メモ

作成: 2026-11-10 / 状態: 叩き台（鬼塚さんとのMTG前）

## 目的と全体像
Link up の各店舗シートは**そのまま**使い、そこから「汎用FMT（縦持ち）」を作り、BigQuery に入れて分析・AIMB 表示に使う。
汎用FMTは Link up 専用にせず、他社からの相談でも「このFMTに入力すれば整形データとして扱える」状態を目指す。

```
Link up 各店舗シート（そのまま） → Python（extract_linkup.py） → 汎用FMT（CSV/シート） → BigQuery
```

## 汎用FMT（縦持ち）
1行に数字を1つ。値は数値のみ。項目の意味は指標ごとに自由に決める。

| 列 | 意味 |
|---|---|
| date | 日付 |
| company | 会社 |
| metric | 指標（指標定義の候補から選ぶ） |
| item1〜item10 | 項目（意味は指標ごと。使わない項目は空。2026-11-10 に鬼塚さんの提案で5→10個） |
| kind | count（件数など）/ ratio（比率）。BigQuery で軽くするため短い値（鬼塚さんの提案） |
| value | 数値（BigQuery では FLOAT64） |
| source_file | 取り込み元のファイル名（変換プログラムが付ける） |
| loaded_at | 取り込み日時（UTC。変換プログラムが付ける） |

Link up の次回予約: item1=店舗 / item2=スタッフ / item3=媒体（通常・ミニモ）/ item4=新規・再来 / item5〜10=空。
指標: 来店客数・次回予約数・指名数（count）、次回予約率（ratio）。

ルール:
- ratio は 0〜1（80% は 0.8。比率は一般に 0〜1 で扱うため）。画面に出すときに 100 倍して「%」を付ける。次回予約率 = 次回予約数 ÷ 来店客数（小数第3位）。来店客数 0 の行は作らない。
- **ratio の行は表示用。集計は count から計算し直す**（比率は足し算できない）。
- 足し算で全体になる粒度で入れる（ミニモは新規・再来に足し算の関係。全体は通常+ミニモで計算）。
- 休みの日は行を作らない。0 は行を作る。

## アプリとの接続（二層構成、エカテリーナさん提案 2026-11-11。方向性は賛成、詳細は調整中）
```
[1] raw_metrics（この汎用FMTのまま）→ 対応表3つ（metric_map / store_map / staff_map）→ [2] extra_metrics_monthly → アプリ（汎用の「追加指標」エンドポイントとカード）
```
- [1] raw_metrics: company, date, metric, item1〜10, kind, value + source_file, loaded_at。item は常に文字列、value は FLOAT64。
  ユニークキーは (company, date, metric, item1〜10)。再取り込みは洗い替え。
- [2] extra_metrics_monthly: company_id, store_name, stylist_name, month, metric_id, value。store_name / stylist_name は POS の月次テーブル（all_pos_monthly）と完全一致の文字列。
- 対応表は会社ごとの小さい表で、コードには書かない（会社を増やすときは行を足すだけ）。
- POS の名前: 店舗は「sofa国分寺」「shell国分寺店」「shell立川」と「店」の有無がばらばら。スタッフは sofa・Ada が「氏名【国分寺】」（全角スペースの人もいる）、shell・tokute は氏名のみ。シート上の名前のままでは POS と繋がらないため、staff_map / store_map で変換する。

決まっていない点（返信済み・または返信待ち）:
- 洗い替えの単位: 「company × 月」だと、1店舗ぶんの再取り込みで同じ月の他店舗のデータが消える。「company × 月 × source_file」か、全店舗を同時に取り込む運用にする
- metric_id の粒度: [2] には媒体・新規/再来の列がないため、metric_map で（指標＋媒体＋新規/再来）を metric_id に割り当てる。通常/ミニモを合算するか、新規/再来を分けるか
- 月次の比率: 取得数の合計 ÷ 来店客数の合計で計算し直す（日ごとの ratio は足さない）。raw の ratio の行は月次の層では使わない前提
- staff_map: POS にいない人（ヘルプ、Ada の「さら・ゆう・りん」など）は、捨てずに未対応として一覧に出す
- 使わない項目の空文字か NULL か: NULL どうしは「等しい」と判定されず、キーの照合（MERGE・結合）で二重に入る恐れがある。キーの列は空文字にそろえる案（NULL なら比較で COALESCE が必須）

## 鬼塚さんの設計ドキュメントとの対応と決定事項（2026-11-12 確認、11-13 鬼塚さん承認）
ドキュメント「AI-ManagementBoard_自由項目オプション_要件」は、この設計と合っている（洗い替えは company×期間、使わない item は空文字、metric_id は内訳を足し合わせた粒度、アプリ入力は source_file 単位で洗い替え）。
### エカテリーナさんの回答（2026-11-16 14:28）で決まったこと
- 洗い替え: company × 月 × source_file で賛成。条件は source_file が取込のたびに同じ名前になること。名前が変わった場合は company × 月で手動で消す。→ `extract_linkup.py` は source_file を店舗ごとの固定名 `linkup_<店舗>` にした（ダウンロード名は使わない）。
- metric_id: 新規/再来は分ける、通常/ミニモは合算（媒体の内訳は [1] raw に残る）。[2] の Link up 分は次の5つ。率（`next_booking_rate_new` など）と合計（`_total`）はビューで計算し、[2] には持たない。
  - 来店客数 × 新規 → `visit_count_new` / × 再来 → `visit_count_repeat`
  - 次回予約数 × 新規 → `next_booking_count_new` / × 再来 → `next_booking_count_repeat`
  - 指名数 → `nomination_count`
- **ratio の行は [2] に渡さない**（[1] raw には確認用に残す。[1]→[2] の変換では kind=ratio を除く）。
- 空文字 `''` で統一。[1] の item1〜10 は未使用なら `''`、取込側でも `COALESCE(item, '')` をかける（`make_row` は対応済み）。

名前の表記ゆれ: 人が直接入力する会社は、店舗・スタッフ名を POS の名前のプルダウンで選ばせる（名簿シートを追加し、指標定義で「名簿から選ぶ」項目を指定する案）。Link up のようにシートから読み取る場合は防げないので、5.4「対応表で変換できない行はエラー」で受ける。
決定（鬼塚さん承認）:
1. staff_map に「対象外」を指定できるようにする（POS にいない名前、ヘルプや Ada の さら・ゆう・りん が毎朝エラーにならないように）
2. 日付は `2026-09-01` の形式にそろえる（BigQuery に入れやすい。ドキュメントの `yyyy/mm/dd` から変更）
3. 指標数の上限3つの数え方は、表示用の ratio（次回予約率）は数えない（Link up は来店客数・次回予約数・指名数の3つ）
未対応: 対応表（metric_map / store_map / staff_map）の作成、「対象外」の実装（対応表の実装時）、テンプレートの名簿シート・プルダウン。
