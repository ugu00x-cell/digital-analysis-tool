# Claude Codeへの指示文の書き方

## 目的

Claude Codeのような開発AIエージェントに作業を依頼する際、平文の指示は曖昧さを生みやすく、AIとの往復確認や意図しないリファクタリングなど、想定外のコストにつながりやすい。本ドキュメントでは、誤解を減らし、AIが一度で正しく作業に着手できる指示文の書き方をまとめる。

## 手順

1. **タスク概要を1行で明記する**
   何をしてほしいのか（バグ修正・機能追加・リファクタリング等）を最初に短く言い切る。AIが最初に読む情報がここになるため、目的の取り違えを防げる。

2. **背景・現状を具体的に書く**
   「エラーが出る」ではなく、実際のエラーメッセージ（スタックトレース）、発生条件、コードの経緯（いつ書いたか・なぜ改修が必要か）を書く。曖昧な現状説明は、AI側からの追加質問という往復コストを生む。

3. **要件（やること）と禁止事項（やらないこと）を分けて列挙する**
   「ついでに整理して」のような曖昧な依頼は、AIの裁量に任せる範囲が広がりすぎる。対象範囲を明示し、変更してはいけない箇所（URL・出力形式・依存ライブラリなど）を禁止事項として先に釘を刺す。

4. **完了条件をチェックリスト形式で示す**
   「動けばOK」ではなく、実行結果・ログ出力・コード品質など、検証可能な条件を箇条書きにする。これにより「直った」の判断が主観ではなく客観的な基準になる。

5. **参考情報（環境・対象）を埋めて送信前に空欄チェックする**
   バージョン情報や対象ファイルパスなど、変数となる部分を必ず実値で埋める。テンプレートの型がどれだけ優れていても、プレースホルダーが残っていればAIは作業に着手できない。

## 注意事項

- テンプレートを使い回す際は、送信前に `〔　〕` や `（ここに貼り付ける）` のようなプレースホルダーが残っていないか必ず確認する
- 対象ファイルが複数案件にまたがる場合（同名ファイルが複数リポジトリに存在する等）は、パスを明記しないとAI側が対象を特定できず、誤った案件のコードに触れるリスクがある
- 禁止事項は「やってほしくないこと」を具体的に書く。抽象的な注意書き（「気をつけて」等）では暴走を防げない

## まとめ

| 項目 | 平文指示 | 構造化指示 |
|---|---|---|
| エラー内容の具体性 | 低い（推測が必要） | 高い（メッセージを明記） |
| 作業範囲の境界 | 曖昧（AI裁量任せ） | 明確（要件と禁止事項で分離） |
| 完了判定 | 主観的 | 客観的（チェックリスト） |
| AIとの往復回数 | 多くなりやすい | 少なくなりやすい |
| 暴走・誤修正のリスク | 高い | 低い |
