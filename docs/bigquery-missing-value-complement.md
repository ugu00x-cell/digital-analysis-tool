# BigQuery欠損値補完の作業手順

## 目的

BigQuery上のマスタテーブルに存在する欠損値（郵便番号・駅名・沿線名・土地権利区分・総戸数など）を、既存データの活用とスクレイピングを組み合わせて補完し、データの完全性を高める。誤字や誤補完を防ぎながら、補完済みデータの信頼性を担保することを目的とする。

## 手順

1. **対象範囲の絞り込み**
   欠損項目ごとに全件をスキャンし、実際に補完が必要な行を条件で絞り込む（例：`customer_data`にリードが存在する行のみ、特定カラムがNULLの行のみ）。範囲を絞ることで、後工程の目視チェック負荷を現実的な量に抑える。

2. **既存データからの反映を優先する**
   外部API・スクレイピングに頼る前に、社内の他テーブル（`project_info`等）に既に存在する情報がないか確認し、あれば先に反映する。コストゼロで補完率を稼げるため、最初に実施する。

3. **不足分をスクレイピングで補完する**
   既存データで埋まらない項目は、対象サイト（SUUMO等）をSeleniumやBeautifulSoupで取得し補完する。取得できなかった項目（該当要素なし等）は、推測で埋めず「不明」に統一する。推定値を確定値のように見せないことが重要。

4. **補完実行とBigQueryへの反映**
   カラム追加（例：`yubinkodo1`, `yubinkodo2`）が必要な場合は事前に実施し、型不一致によるサイレント失敗（INT64列にNULLリテラルを渡す等）を避けるため、NULLは明示的にキャスト（`CAST(NULL AS STRING)`）して書き込む。

5. **全件ファクトチェックを実施する**
   補完後は必ず全件を目視スキャンし、以下を確認する：重複登録の有無、数値項目への不正な非数値混入、表記ゆれ・誤字（特に難読漢字はコンソール直接入力で誤字が頻発しやすい）、コードポイント単位での文字化けチェック。

## 注意事項

- BigQueryコンソールへの直接タイプ操作は難読漢字の誤字が非常に発生しやすい（団→團、鉄→鐵等）。都度SELECTで確認し、コードポイント単位で修正する運用を徹底する
- 一括UPDATE（`biko LIKE '%推定%'`等の条件指定）は、意図しないカラムまで巻き込んで上書き・NULL化するリスクがある。実行前に対象行を絞り込み、実行後に再点検を行う
- 機械的・目視チェックはデータの整合性（重複・型・表記ゆれ）は担保できるが、内容そのものの事実確認（住所・徒歩分数の実在性等）まではカバーしない。納品前にクライアント自身の最終スポットチェックを推奨する旨を必ず伝える

## まとめ

| 工程 | 目的 | リスク・注意点 |
|---|---|---|
| 対象範囲の絞り込み | チェック負荷を現実的な量に抑える | 条件漏れで対象外データが残るリスク |
| 既存データの反映 | コストゼロで補完率を稼ぐ | データの鮮度・正確性の事前確認が必要 |
| スクレイピングによる補完 | 外部情報源からの取得 | 該当要素なし時は「不明」に統一し、推定を確定のように見せない |
| BigQueryへの反映 | 補完結果の永続化 | 型不一致によるサイレント失敗に注意（明示キャスト必須） |
| 全件ファクトチェック | データ品質の担保 | 難読漢字の誤字・一括UPDATEの巻き込み事故に注意 |
