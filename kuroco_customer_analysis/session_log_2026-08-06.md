# KUROCO案件 customer_data分析 セッションログ（2026-08-06）

## 1. データ構造の初期調査
- クライアントより `dj-ga4.scd.customer_data`（新築分譲マンション販売リード情報）の分析を依頼
- `column_name_mapping`テーブルでカラム名の日英対訳を確認
- **重大発見**：`id`／`id_2`／`kanribangou`はいずれも個人を一意に識別するキーではない（`id`は57種、`id_2`は実質1種、`kanribangou`は42種の分類コード）
- クライアントに確認 → 「1行1名」で扱う方針で合意（複数物件・複数申込は重複カウントされる仕様と確認）
- データ範囲条件（2023/01/01以降・社内オープンデータのみ）は既にテーブル側で反映済みと確認
- `kokyakuoopunjoukyou_bunseki`（オープン状況）が全行"1.0"で統一 → クローズデータはアクセス範囲外と判断
- 192件だけ`kokyakuoopunsettei_bunseki`が空欄だった件 → 実害軽微と判断し無視

## 4. 通勤時間分析（当初計画：頓挫）
- Google Maps Directions API（TRANSIT・乗換案内モード）で①住居→②勤務地、②→③購入物件の駅間移動時間取得を計画
- APIキー発行・サービスアカウント作成・BigQuery権限付与まで完了
- **重大判明**：Google Maps PlatformはTRANSIT（電車）モードが日本の交通事業者に非対応（公式ドキュメントで確認）。DRIVEモードは正常動作
- クライアントと相談し、簡易指標として「駅間の直線距離」に方針変更

## 5. 直線距離分析への切り替え・実装
- Geocoding APIで駅名→緯度経度変換、BigQueryの`ST_DISTANCE`で直線距離を算出する方式に実装変更
- 海外地名への誤マッチ（例：「San Jose, California」）を発見 → 国コード（JP）でフィルタする修正を実施
- 4,294件のユニーク駅名をジオコーディング（4,200件成功、無料枠内）
- JOIN時の駅名正規化バグ（「駅」サフィックスの有無）を発見・修正 → マッチ件数が18件→52,524件に改善

## 6. 分析結果
- **直線距離帯別契約率**：0〜50km以上のどの距離帯でも18〜22%程度で明確な相関なし
- **物件価格帯別契約率**：3000〜4000万円で14.6%、価格が上がるほど低下し8000万円以上で3.1%（明確な相関あり）
- **価格帯×距離帯クロス集計**：契約率を左右しているのは主に価格。距離の影響は相対的に小さい
- **50km以上セグメントの都道府県別**：千葉・茨城・埼玉など郊外物件に集中
- **予算×成約金額ヒートマップ**：自己申告予算と実際の成約額はおおむね一致するが、予算より一段階上の物件を選ぶ傾向もあり
- **重要な注意点（ユーザー指摘により追記）**：
  - 「通勤の近さ」ではなく「直線距離」でしか測定できていない（実際の乗換・所要時間は不明）
  - 「予算(yosankingaku)」と「実際の成約金額(baibaidaikinzeikomikakaku)」は別指標であり、価格帯分析には後者を使うべき
  - プロジェクトごとの顧客数に大きな偏りがあり（最大7,276件〜最小1件）、契約率の結論が一部の大規模プロジェクトに引っ張られている可能性
  - 「プロジェクト」と「物件」は別概念（project_infoに物件名6,099件・プロジェクトコード4,794件、1対1ではない）
