## はじめに：なぜ今MES・ERPを学ぶのか

製造業DXという言葉が飛び交っている。だが現場の実態はどうか。

Excelで生産日報を管理し、品質データは紙の検査成績書に手書き。設備の稼働状況は担当者の肌感覚。私が15年間見てきた製造現場の多くがこれだ。

DXの第一歩は、現場のデータを「見える化」して経営判断につなげること。そのときに必ず出てくるのが **ERP** と **MES** という2つのシステムだ。

しかし、現場エンジニアにとってこの2つは馴染みが薄い。導入しているのは情シス部門やIT部門で、現場には「なんか入れられたシステム」という認識のことが多い。

これではDXは進まない。現場を知っているエンジニアこそ、MES・ERPの本質を理解すべきだ。品質管理10年・加工技術5年の立場から、実務者目線で整理する。

## ERPとは何か：工場の「経営の目」

**ERP（Enterprise Resource Planning）は、会社全体のヒト・モノ・カネを一元管理するシステムだ。**

製造業での主な機能はこうなる。

| 機能 | 具体例 |
|------|--------|
| 生産計画 | 月次・週次の生産数量を計画する |
| 購買管理 | 材料・部品の発注を管理する |
| 在庫管理 | 原材料・仕掛品・完成品の在庫を把握する |
| 原価管理 | 製品ごとの原価を計算する |
| 販売管理 | 受注から出荷・売上までを管理する |
| 会計 | 財務諸表を生成する |

代表的な製品はSAP、Oracle、富士通GLOVIA、MCFrameなど。

### 現場エンジニアが押さえるべきポイント

ERPは **「経営層が意思決定するためのシステム」** だ。工場の現場作業を管理するものではない。

例えば、ERPは「今月1,000個作る」という計画は持っている。だが「今日の3号機の午前シフトで何個作ったか」「設備が10時に停止した」といった現場のリアルタイム情報は持っていない。

ここがよく混同されるところだ。ERPに現場の詳細を求めてはいけない。それはMESの仕事になる。

## MESとは何か：工場現場の「実行の目」

**MES（Manufacturing Execution System）は、工場の製造現場をリアルタイムで管理・実行するシステムだ。**

ISA-95（国際標準規格）では、MESの機能を11カテゴリに定義している。製造業エンジニアが特に関わる主要機能を整理する。

| 機能 | 現場での意味 |
|------|-------------|
| 作業スケジューリング | 設備ごと・ラインごとの詳細な作業順序を決める |
| 作業指示 | 作業者に「何を・どの設備で・どの条件で」を指示する |
| データ収集 | 設備の稼働データ・加工条件・検査結果を自動収集する |
| 品質管理 | SPC（統計的工程管理）、Cpk管理、不良トレーサビリティ |
| 設備保全管理 | 設備の状態監視、予防保全のトリガー管理 |
| 実績管理 | 生産数量・歩留まり・サイクルタイムの実績を記録する |

工作機械メーカーの現場では、FANUCのMT-LINKiのように設備のCNC装置から直接データを吸い上げる仕組みがMESの入口になることが多い。自社製のマシニングセンタが何台も並ぶ工場で、各設備の稼働状態・アラーム・加工実績をリアルタイムに集約する。これが「現場の見える化」の最小単位だ。

大規模なMES製品（Siemens Opcenterなど）をフルスペックで導入する工場もあるが、中堅規模の工場では設備データ収集から段階的に入るケースの方が現実的だ。

### 現場エンジニアが押さえるべきポイント

MESは **「現場の今を見て、現場を動かすシステム」** だ。

品質管理の立場で言えば、MESがあると以下が変わる。

- 検査データが手書きではなく自動収集される
- Cpkがリアルタイムで算出される
- 工程異常が発生した瞬間にアラートが飛ぶ
- 不良品のトレーサビリティが「いつ・どの設備で・どの材料ロットで」まで追える

逆に言えば、MESがない現場ではこれらを人手でやっている。Excelで品質データを集計し、月次会議で報告する頃には、もう手遅れだ。

## ERPとMESの違いと連携

この2つは「対立するもの」ではなく、 **「階層が違うもの」** だ。

```
┌─────────────────────────────────┐
│          ERP（経営層）            │  月次・週次の計画と実績
│    生産計画 / 原価 / 在庫 / 会計   │
├─────────────────────────────────┤
│          MES（現場管理層）         │  日次・リアルタイムの実行と管理
│  作業指示 / データ収集 / 品質 / 保全 │
├─────────────────────────────────┤
│       制御層（PLC・設備）          │  秒単位の設備制御
│    NC装置 / ロボット / センサー     │
└─────────────────────────────────┘
```

### 連携の流れ

1. **ERP → MES**：「今週、製品Aを500個作れ」という生産計画が降りてくる
2. **MES**：計画を受けて、設備・作業者・材料を割り当て、作業指示を出す。実行中のデータを収集する
3. **MES → ERP**：「今週、製品Aを480個作った。不良20個。設備稼働率85%」と実績を返す

このデータの往復が、経営判断と現場実行をつなぐ。

### よくある失敗パターン

**ERPだけ導入してMESがない工場。** これが最も多い。

ERPに生産計画は入っているが、現場の実績は手入力。タイムラグは数日。データの粒度は粗い。結果、ERPの計画と現場の実態が乖離し、「システムが使えない」と現場から不満が出る。

原因はERPではなく、MES不在による現場データの欠落だ。ERPは悪くない。間にMESがないことが問題だ。

## PythonでMESデータを分析する可能性

MESが導入されると、現場から大量のデータが取れるようになる。ここからがエンジニアの出番だ。

MESのデータをPythonで分析することで、以下のような価値が生まれる。

### 1. MESのDBからODBCで直接データを引く

MESのデータはたいていSQL ServerやOracleなどのRDBに格納されている。PythonからODBC経由で直接接続すれば、MESの標準画面では出せない切り口で分析できる。

```python
# MESのDBからODBC経由で検査実績を取得する例
import pyodbc
import pandas as pd

def fetch_inspection_data(
    dsn: str, start_date: str, end_date: str
) -> pd.DataFrame:
    """MESのDBから指定期間の検査実績を取得する"""
    conn = pyodbc.connect(f"DSN={dsn};Trusted_Connection=yes;")
    query = """
        SELECT
            m.machine_id,          -- 設備番号
            m.machine_name,        -- 設備名
            i.part_number,         -- 品番
            i.measured_value,      -- 測定値
            i.usl,                 -- 上限規格
            i.lsl,                 -- 下限規格
            i.inspection_datetime, -- 検査日時
            i.lot_number,          -- 材料ロット番号
            i.operator_id          -- 作業者ID
        FROM inspection_results i
        INNER JOIN machines m ON i.machine_id = m.machine_id
        WHERE i.inspection_datetime BETWEEN ? AND ?
        ORDER BY i.inspection_datetime
    """
    df = pd.read_sql(query, conn, params=[start_date, end_date])
    conn.close()
    return df
```

このDataFrameがあれば、「設備別×ロット別のCpk推移」「特定の時間帯に集中する不良パターン」など、MESの画面では数クリックかかる分析がpandasの数行で終わる。

### 2. 設備稼働データからOEEを自動算出する

設備のサイクルタイム・停止時間・アラーム履歴をMESのDBから取得し、OEE（設備総合効率）を自動算出してPlotlyでダッシュボード化する。MESの標準レポートは日次・週次が多いが、Pythonなら任意の時間粒度でドリルダウンできる。

### 3. 品質データ×加工条件のクロス分析

MESの強みは、品質データと加工条件データが同じDBに入っていることだ。検査結果テーブルと加工条件テーブルをJOINすれば、「どの設備で・どの材料ロットで・どの送り速度のとき不良率が上がるか」をscikit-learnで統計的に解析できる。

### 現場エンジニアがPythonを使う意味

ここが重要だ。MESベンダーの標準ダッシュボードでは、現場固有の分析ニーズに対応しきれない。

ベンダーにカスタムレポートを依頼すると、1画面あたり数十万円、納期は数週間。だがPythonでODBC接続すれば、自分で同じことが半日でできる。

「うちの工場ではこの指標を毎朝見たい」「この加工条件と不良率の関係を可視化したい」という要求は、現場を知っている人間にしか出せない。そしてそれを自前で実装できれば、ベンダーへの依頼コストと待ち時間をゼロにできる。

私の実感として、MESの分析レポートをベンダーに外注する工場と、現場エンジニアが自前で書く工場では、PDCAの回転速度が全く違う。前者は月1回の報告会で議論する。後者は翌朝には原因と対策が出ている。

## まとめ

| 項目 | ERP | MES |
|------|-----|-----|
| 管理の対象 | 会社全体の経営資源 | 工場現場の製造実行 |
| データの粒度 | 月次・週次 | 日次・リアルタイム |
| 主なユーザー | 経営層・管理部門 | 現場管理者・作業者 |
| 扱うデータ | 計画・原価・在庫・売上 | 作業指示・品質・設備稼働 |
| Pythonとの親和性 | BIツール経由が多い | データ分析の宝庫 |

経産省のDXレポートでは、製造業の約7割がDXに着手しているとされる。だがその多くはERPの導入や基幹システムの刷新であり、現場のMES層は手つかずのままだ。

結果、「DX推進中」と経営層は言うが、現場の品質データは相変わらずExcelで集計され、設備の停止原因は作業者の記憶に依存している。ERPとMESの間に空白がある工場は、まだ山ほどある。

この空白を埋められるのは、現場を知っていてコードが書ける人間だ。MESのDBにODBCで接続し、必要な分析を自前で書く。ベンダーに依頼すれば数十万円・数週間かかるレポートを、半日で作る。そういう人材は、製造業の求人市場では極めて少ない。

まずは自分の工場が今どの階層のデータを持っていて、どこが欠けているかを見てほしい。ERP・MES・制御層の3階層のうち、MES層が空白なら、そこがDXの最大のボトルネックであり、同時に最大のチャンスだ。
