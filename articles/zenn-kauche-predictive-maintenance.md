## この記事の結論

カウシェが作った「PRの83%をAIレビューだけで自動マージする仕組み」。
その構造を読んだとき、私は手が止まった。

**これ、予知保全パイプラインと全く同じだ。**

品質管理10年、加工技術5年。工作機械メーカーで現場を見てきた人間が、ソフトウェア開発の最前線に同じ構造を見つけた話を書く。

## カウシェが何をやったか

カウシェはシェア買いアプリを運営するスタートアップだ。
彼らはClaude Code Actionを使い、AIコードレビューの自動化に取り組んだ。

仕組みはこうだ。

PRが出ると、3人のAI専門家が並列でレビューする。
シニアGoエンジニア、アーキテクト、GCPインフラ専門家。
それぞれが「BUG（マージ阻止）」と「SUGGESTION（提案）」に指摘を分類する。

BUGがゼロなら、人間のレビューなしで自動マージされる。
結果、全PRの83%がAIレビューだけで通るようになった。

ここまでなら「すごい自動化だな」で終わる。
本当に面白いのは、その裏側にある改善ループだ。

## 毎晩回る5つのエージェント

カウシェのシステムには、毎晩動く5つのエージェントがいる。

| エージェント | 役割 |
|---|---|
| Measure | PR統計を集計する。承認率、誤判定数、ルール発火率 |
| Explore | リポジトリを巡回し、見えないボトルネックを探す |
| Improve | 実際にレビュールールを編集する |
| Reflect | 3つの出力から、翌日の優先順位を決める |
| Audit | 改善が逆効果を起こしていないか検証する |

このループが毎晩回ることで、レビュールールが自動で進化していく。

ここで私は気づいた。

## 予知保全パイプラインとの対応関係

私はいま、ベアリングの異常検知システムを開発している。
振動センサーのデータからRMS値（振動の大きさの指標）を計算し、劣化の兆候を検知する仕組みだ。

カウシェの記事を読み進めるほど、対応関係が浮かび上がってきた。

| AIコードレビュー | 予知保全 |
|---|---|
| PRのdiff（変更差分） | センサーの振動データ |
| コードレビュー | 異常判定アルゴリズム |
| Approve / Reject | 正常 / 異常 |
| 見逃し（バグが本番へ） | 見逃し（異常を正常と判定） |
| レビュールール | 判定しきい値・特徴量ルール |
| 毎晩のルール改善ループ | しきい値の自動チューニング |
| 思考ジャーナル | 誤検知パターンの記録と引き継ぎ |

表にすると一目瞭然だが、本質は1行で言える。

**どちらも「連続的な入力から異常を検知し、判定ルールを自動改善する」システムだ。**

## 「何を見ないかで精度が決まる」

カウシェの記事で最も刺さった一文がある。

> 何を見つけるかではなく、何を見ないかで精度が決まる

AIレビューでは、指摘を増やすほど精度が下がる。
ノイズが増えて、本当に止めるべきバグが埋もれるからだ。
だからカウシェは「効果スコア」でルールを評価し、発火しても無視されるルールを削る。

予知保全でも全く同じ問題が起きる。

しきい値を厳しくすれば、異常は見逃さない。
だが誤報（偽陽性）が増え、現場は「またか」とアラームを無視し始める。
これを「アラーム疲れ」と呼ぶ。

工場の現場で一番怖いのは、異常を見逃すことではない。
**アラームが信用されなくなることだ。**

カウシェのシステムが「見ないものを決める」のと同じように、予知保全でも「鳴らさないアラームを決める」ことが精度を左右する。

## 予知保全に持ち帰れる設計

カウシェの構造から、予知保全側に持ち帰れる設計が3つある。

### 1. 段階的アラーム

カウシェはBUGとSUGGESTIONで指摘を分ける。
予知保全でも、アラームを段階化すべきだ。

```
注意（120%）：ログに記録。現場には通知しない
警告（150%）：担当者に通知。次の定期点検で確認
危険（200%）：即座にライン停止を推奨
```

全部を同じ重さで鳴らすから、アラーム疲れが起きる。

### 2. 遅延フィードバックループ

カウシェは毎晩のバッチでルールを改善する。
予知保全でも同じループを組める。

```
アラーム発報 → 現場が確認 → 実際に異常だったか記録
→ ラベル付け → 判定ルールの精度を再評価
→ しきい値を自動調整
```

製造業の現場では、確認結果が返ってくるまで数時間〜数日かかる。
だからこそ「遅延フィードバック」を前提とした設計が必要だ。
リアルタイムに正解がわからない点も、コードレビューと同じだ。

### 3. 思考ジャーナル（誤検知パターンの記録）

カウシェの各エージェントは、毎回新規セッションで起動する。
だから「前回の判断記録（思考ジャーナル）」を読み込んで判断の連続性を保つ。

予知保全でも、これは有効だ。

```
2026-04-01：Bearing1_3でRMS急上昇→現場確認→潤滑剤補充直後のノイズだった
2026-04-05：同パターン検出→潤滑剤補充履歴と照合→アラーム抑制
```

誤検知のパターンを記録し、次の判定で参照する。
人間が引き継ぎメモを書くように、システムにも記憶を持たせる。

## なぜこの構造が見えたのか

私はエンジニア職歴ゼロだ。Pythonは独学で、バイブコーディングで動くものを作っている。

でも、製造業の現場で15年間やってきたことがある。
「データを見て、異常を判定して、ルールを改善する」。
これは品質管理そのものだ。

カウシェの記事を読んで、ソフトウェアの世界でも同じことをやっていると知った。
ドメインが違うだけで、構造は同じだ。

工場のセンサーデータもPRのdiffも、本質は「変化の信号」だ。
その信号から異常を見つけ、見逃しを減らし、誤報を抑える。
そして判定ルールを自動で育てていく。

**製造業の品質管理は、ソフトウェアの品質管理と同じ問題を解いている。**

## まとめ

カウシェのAIコードレビューから学んだことを3つに絞る。

1. **段階的に判定する**。全部を同じ重さで扱わない
2. **遅延フィードバックを前提にする**。正解はすぐには返ってこない
3. **判断の記録を残す**。システムに記憶を持たせて、同じ誤判定を繰り返さない

予知保全の精度は、アルゴリズムの性能だけでは決まらない。
**「何を鳴らさないか」を設計できるかで決まる。**
